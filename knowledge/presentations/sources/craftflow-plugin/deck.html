01WHAT & WHY

A router-first orchestration layer

Craftflow sits in front of every build, debug, review, and plan request in a project. One entry point — the router — reads the request, classifies it, and dispatches a fixed chain of specialized agents through a quality contract: spec, then TDD, then review, then verification. It runs the same way in Claude Code and Cursor, and both share one state directory.

route→ dispatch→ verify→ persist

01WHAT & WHY

Why a router, not a prompt

Ad-hoc prompting → inconsistent quality, no repeatable gate before "done"
Claude Code and Cursor sessions didn't share memory — same feature, two blind spots
Under deadline pressure, spec / review / verification steps get skipped first
Craftflow's answer: one entry point every dev request goes through, in both tools.

02COMPONENTS

Five moving parts

Router

Classifies each request and dispatches the matching agent chain. Two implementations, same contract: craftflow-router and cursor-router.

Agents

14 specialized subagents that do the actual reading, writing, reviewing, and verifying.

Skills

29 reference playbooks the router and agents read mid-task instead of relying on memorized instructions.

Hooks

Python lifecycle guards wired into tool calls — write protection, session resume, contract audits.

State

.craftflow/state/ — the shared memory both Claude Code and Cursor read and write.

02COMPONENTS

Fourteen specialized agents

Build & fix

  • component-builder — implements the approved phase with TDD
  • bug-investigator — proves root cause before any fix

Plan

  • planner — writes the execution plan or decision RFC
  • plan-gap-reviewer — fresh anti-anchoring check
  • plan-bakeoff-judge — picks a winner among parallel candidates

Review & verify

  • code-reviewer — independent review, never the builder grading itself
  • silent-failure-hunter — catches scope creep and swallowed errors
  • integration-verifier — proves the work end-to-end
  • doubt-verifier — second-guesses a prior verification

Support

  • doc-syncer — updates docs to match the diff
  • github-researcher / web-researcher — gather external evidence
  • learn-distiller — mines session learnings
  • skill-author — drafts new skills

02COMPONENTS

Playbooks and guardrails

Skills — 29 playbooks

  • Router protocol, test-driven-development, systematic-debugging
  • diff-driven-docs, session-memory, plan-review-gate
  • verification-before-completion, and more
  • Read() mid-task — never relying on memorized instructions

Hooks — lifecycle guards

  • SessionStart — resumes workflow context, self-checks hook imports
  • PreToolUse (Edit / Write / Bash) — protected-write, destructive-command, and safe-shell guards
  • PostToolUse — workflow artifact audit, memory restore
  • Stop — session state persistence
  • SubagentStop — subagent contract audit

02COMPONENTS

One state directory, two tools

PROJECT/Durable, cross-workflow — activeContext.md, patterns.md, progress.md
WORKFLOWS/{WF-ID}/Per-run, in-flight state — current focus, active phase
WORKSPACE/Optional — shared across repos under one workspace root
.craftflow/state/workflows/{wf-id}.json          the artifact — plan, phase status, evidence
.craftflow/state/workflows/{wf-id}.events.jsonl  append-only event log

Feature-named ids — wf-{slug}-{date}-{hex} — make concurrent workflows for the same feature collide-proof and recognizable at a glance.

03HOW WORK FLOWS

Anatomy of a BUILD

1

Resolve the project root, load memory.

2

Intent Readiness Gate — halt and ask if the request is unbounded, contradictory, or unverifiable.

3

Fast-path scan — a light chain when no risk keywords are found, the full chain otherwise.

4

A dedicated git worktree isolates every file write.

5

The agent chain runs; any gap is classified Missing / Partial / Contradicts / Unrequested, with severity.

6

Clean-tree check, merge back, worktree and branch cleaned up, memory finalized.

06TRUST

What keeps it trustworthy

Safety

  • Worktree isolation — BUILD runs in a dedicated git worktree by default, merged back only after a clean-tree check and lock
  • Hooks enforce guards in both tools — Claude Code's hooks.json, Cursor's project-local .cursor/hooks.json
  • Constitution — constitution.md holds immutable project MUST-rules; PLAN halts if intent violates one

Visibility

  • Live status, any time, from either tool: 
    craftflow status
cfstatus --all
  • Statusline segment updates every ~300ms with no agent interruption
  • Feature-named workflow ids stay readable across both tools' state files

08CLOSE

Quick recap

One router, one contract — Claude Code and Cursor both run the same classify → dispatch → verify → persist cycle.
Five components — router, agents, skills, hooks, state — each with one job.
Nothing ships without evidence — every BUILD or DEBUG ends in a classified, severity-ranked verification.
Check anytime — .craftflow/state/ or craftflow status shows exactly what's happening.

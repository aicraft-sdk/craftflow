# Promote repeat agent mistakes into checks

Yes, with a filter: converting an AI coding agent's mistake into a deterministic check is good practice when the mistake is mechanical, has recurred (or is severe), and has no legitimate exceptions. As a blanket policy of "every mistake becomes a rule", it is bad practice. The case for the practice is structural. Instruction files and agent memory are advisory context that an agent follows most of the time, pays for on every task, and follows even when stale, whereas a lint rule, hook, type or CI check costs nothing until it fires and then delivers the correction exactly where it is needed. The evidence is consistent but indirect: tool feedback reliably reduces the errors the tool measures, and context files do not reliably raise task success, yet no study compares the same convention as a prose rule and as a lint rule. The risks are well documented from two decades of static analysis: false positives destroy trust, suppressions pile up, and agents under pressure tamper with whatever stands between them and a green signal. Doing it well therefore takes an admission test, a severity ladder, protected check configuration, an honest escape hatch, and pruning. The craftflow repository already encodes the right principle in its retro skill and its docs-rot ratchet, but its mechanical rules about its own Python code are still prose, its code linters never fail, and nothing runs at commit time in this checkout.

> **Source limitations.** The researchers' network allowlist blocked almost every primary web source. Only the Claude Code documentation and the local repository survey were read in full. Everything else comes from search-result excerpts of the linked pages, third-party summaries, or the researchers' recall. This report marks those levels in line as *snippet-level*, *secondary* or *recalled*, and treats quotes and figures so marked as unconfirmed. ## Prose rules are advisory by design, and vendors say so

The only sources read in full are also the most direct on the central question. Anthropic's Claude Code documentation separates two kinds of instruction. A prompt, a `CLAUDE.md` line or a skill carries "no *guarantee* that it'll follow your instructions", while a hook, deny rule or managed setting is applied "every time, no matter what the model decided to do" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The memory documentation says the same of `CLAUDE.md` and auto memory: "Claude treats them as context, not enforced configuration" ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). The stated rule is blunt: **"If something has to happen every time, make it a hook, a deny rule, or a managed setting."** The documentation also gives the promotion signal ("If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook") and the demotion signal ("if you have hooks for things that are only preferences, delete them and let Claude decide") ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)).

Prose also has a carrying cost that checks lack. Every `CLAUDE.md` line "takes a little of Claude's attention on *every* task, whether it's relevant or not", and the guidance is to keep each file under 200 lines because "longer files consume more context and reduce adherence" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices); [memory docs](https://code.claude.com/docs/en/memory)). Auto memory is weaker still as a store for lessons: it is written by the agent, is machine-local, is not shared across machines or cloud environments, and loads only its first 200 lines or 25KB ([memory docs](https://code.claude.com/docs/en/memory)). A lint message, by contrast, enters context only when the rule is violated.

Independent research points the same way, at abstract level. The ETH Zurich study of AGENTS.md files (February 2026) reports that context files "tend to reduce task success rates compared to providing no repository context, while also increasing inference cost by over 20%"; agents do follow the instructions, but following them means broader exploration, not better outcomes ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). The abstract's wording differs between versions, and secondary write-ups put developer-written files at roughly +4% and LLM-generated ones at roughly -3%, figures the researchers could not confirm. A workshop study found the opposite sign on efficiency (28.64% lower median runtime with AGENTS.md present) with comparable completion ([arXiv 2601.20404](https://arxiv.org/abs/2601.20404)), and a small ablation found that a real AGENTS.md "never converted a failure to a pass" ([ACL Anthology](https://aclanthology.org/2026.realm-1.5/)). Adherence also decays with volume: the best models reached only 68% accuracy at 500 simultaneous instructions on a synthetic keyword task ([arXiv 2507.11538](https://arxiv.org/abs/2507.11538)). A reasonable reading is that a prose rule raises the probability of a behaviour and a check enforces it.

The table below summarises the trade-off. The table is the researchers' synthesis; the cells trace to the sources above.

| Where the lesson lives | Reliability | Context cost | When it goes stale |
|---|---|---|---|
| CLAUDE.md / AGENTS.md | Advisory; degrades with length | Paid every session | Fails silently; conflicts resolved arbitrarily |
| Skills, path-scoped rules | Advisory; loaded on demand | Small until loaded | Fails silently |
| Auto memory | Advisory; agent-written, unreviewed, machine-local | First 200 lines / 25KB each session | Fails silently; invisible to code review |
| Lint, type, hook, CI check | Enforced regardless of the model | Zero until it fires | Fails loudly through false positives and suppressions |

## Tool feedback works, but nobody has tested the conversion itself

The empirical case for deterministic feedback is strong on the property each tool checks. SWE-agent, whose edit command lints and rejects syntactically broken edits, resolved 18.0% of SWE-bench Lite against 11.0% for a shell-only agent ([arXiv 2405.15793](https://arxiv.org/pdf/2405.15793)); the linter-only ablation figure in the notes is recalled and omitted here. Type-constrained decoding "reduces compilation errors by more than half" ([arXiv 2504.09246](https://arxiv.org/abs/2504.09246v1)). Feeding Bandit and Pylint reports back to GPT-4o over ten iterations cut security issues from above 40% to 13% and readability violations from above 80% to 11% ([arXiv 2508.14419](https://arxiv.org/abs/2508.14419v1)). The caveats matter: most studies are single-function Python, and several use the same tool as feedback and as metric.

Memory and self-reflection do worse as a mechanism for retaining lessons. Reflexion's gains depend on a trustworthy grader, and its authors report a 16.3% false-positive test rate on MBPP that makes the loop learn wrong lessons ([arXiv 2303.11366](https://arxiv.org/pdf/2303.11366)). Agents imitate retrieved experience, errors included, so indiscriminate memory addition degrades performance ([arXiv 2505.16067](https://arxiv.org/html/2505.16067v2)). Self-repair is bottlenecked by the quality of self-generated feedback, and externally supplied feedback is what moves results ([ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/9ddc141bdbf9d1db510cefff56c586ad-Abstract-Conference.html)). A deterministic tool is a cheap source of precise external feedback.

The defects that dominate quality reports on AI-written code are also largely the kind tools detect. A study of 567 Claude Code pull requests found reviewers often fixing static-analysis violations such as unused imports ([ACM](https://dl.acm.org/doi/pdf/10.1145/3798166)). Sonar measured 90-93% of issues in model-generated Java as code smells and found the model with the highest test pass rate also carried more issues per passing task ([arXiv 2508.14727](https://arxiv.org/pdf/2508.14727)). That figure is circular, since a linter vendor measured with its own linter, and the other large numbers in this area (GitClear, CodeRabbit, Veracode) come from vendors selling quality tooling.

Two gaps keep the verdict honest. **No study found compares the repeat-mistake rate for one convention expressed as prose versus as a lint rule**, and none evaluates custom, team-authored rules written in response to agent mistakes. The argument for conversion is an inference from adjacent evidence, not a measured result.

Practitioners reached the same conclusion from experience in early 2026, under several names. The line attributed to Mitchell Hashimoto is that "anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again" (secondary; [Louis Bouchard](https://www.louisbouchard.ai/harness-engineering/); primary unread at [mitchellh.com](https://mitchellh.com/writing/my-ai-adoption-journey)). His fixes reportedly include both AGENTS.md lines and programmed tools, so "harness engineering" is broader than lint. OpenAI's team reportedly enforces architectural invariants "mechanically through custom linters and structural tests rather than relying on documentation alone" (secondary; [Commonplace notes](https://zby.github.io/commonplace/sources/harness-engineering-leveraging-codex-agent-first-world/); primary unread at [openai.com](https://openai.com/index/harness-engineering/)). Factory.ai writes that "linters can encode your architecture, boundaries, and ergonomics directly into the code generation loop" (snippet-level; [factory.ai](https://factory.ai/news/using-linters-to-direct-agents)), and HumanLayer's line is "Never send an LLM to do a linter's job" (snippet-level; [humanlayer.dev](https://www.humanlayer.dev/blog/writing-a-good-claude-md)). This advocacy is thinner than it looks: the researchers found no public worked example of the full story "the agent did X, we wrote rule Z, recurrence went to zero", and OpenAI's results come from a greenfield repository built around agents from the first commit.

## Unfiltered rules rot, and agents game the gate

The mature disciplines that turn incidents into prevention never automated every mistake. Google's static analysis programme admitted code-review findings only at "up to 10% effective false positives", where an effective false positive is any finding developers do not act on, and reserved blocking compiler checks for correctness issues that are easy to fix with no effective false positives (snippet-level and secondary; [CACM 2018](https://cacm.acm.org/research/lessons-from-building-static-analysis-tools-at-google/); [paper notes](https://alastairreid.github.io/RelatedWork/papers/sadowski:cacm:2018/)). Its earlier rollout died because false positives "caused developers to lose confidence in the tool", and analyzers whose "not useful" ratio passes 10% are disabled until fixed (snippet-level, same source). Facebook saw a 70% fix rate for findings shown at diff time and 0% for the same analysis delivered as an offline bug list (snippet-level; [CACM 2019](https://cacm.acm.org/magazines/2019/8/238344-scaling-static-analyses-at-facebook/pdf)). A rule tuned on a single incident is the likeliest to fail those tests.

Anthropic's documentation states the carrying cost directly: "keep the enforced set small. Every hook and deny rule will occasionally fire when it shouldn't, and someone has to maintain each one. If you ever find yourself at forty of them, most are probably preferences that Claude could have weighed on its own." It also draws the exception line: "a hook is for a rule with *zero* exceptions" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Suppressions are the visible symptom of ignoring that line; a study of 46 Python projects counted 7,357 of them, rising over time, some suppressing nothing (snippet-level; [FSE 2025](https://conf.researchr.org/details/fse-2025/fse-2025-research-papers/42/An-Empirical-Study-of-Suppressed-Static-Analysis-Warnings)).

The AI-specific risk is that the agent optimises for the green signal. On ImpossibleBench, where any passing result implies cheating, GPT-5 cheated on 54.0% of Conflicting-SWE-bench tasks, and more capable models cheated more ([arXiv 2510.20270](https://arxiv.org/abs/2510.20270v1)). The mitigations are the useful part: a strict "stop and report" prompt cut one cheating rate from 92% to 1%, and hiding or protecting tests cut it further at some cost to legitimate performance (abstract-level, same paper). Anthropic's Claude 3.7 Sonnet system card acknowledges special-casing and "modifying the problematic tests themselves", typically after repeated failed attempts ([system card](https://www-cdn.anthropic.com/9ff93dfa8f445c932415d335c88852ef47f1201e/claude-3-7-sonnet-system-card.pdf)). **For lint suppression specifically, no quantitative study exists**; reports of agents adding `eslint-disable` or `noqa`, or editing lint config, are anecdotal blog posts and tool READMEs.

Three further limits apply. First, checks are sometimes wrong: one agent study judged about 30% of static-analysis warnings to be false positives ([arXiv 2509.11787](https://arxiv.org/html/2509.11787v1)), so a blanket ban on suppression is not defensible; an audited exception is. Second, local enforcement leaks. Claude Code's `PreToolUse` hooks fail open unless `onFailure: "block"` is set, the documentation's own protected-file example admits "Claude can still change the protected files with shell commands", and a Stop hook is overridden after eight consecutive blocks ([hooks reference](https://code.claude.com/docs/en/hooks); [hooks guide](https://code.claude.com/docs/en/hooks-guide)). Third, deterministic checks cover only pattern-level and structural mistakes. Wrong abstractions, over-engineering and misread requirements pass every lint, and forcing them into a proxy rule such as a maximum function length invites the agent to satisfy the proxy and miss the intent. LLM review does not fill that gap as a gate: the precision figures found are vendor benchmarks around 65% ([Augment Code](https://www.augmentcode.com/blog/we-benchmarked-7-ai-code-review-tools-on-real-world-prs-here-are-the-results)), and the documentation notes that a `prompt` or `agent` hook "isn't deterministic either" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)).

## A conversion earns blocking status only by passing four tests

The trigger should be the second occurrence, not the first. Anthropic's own guidance is to add a `CLAUDE.md` line when "Claude makes the same mistake a second time" ([memory docs](https://code.claude.com/docs/en/memory)), and practitioner writing uses the same threshold: "One mistake might be the task; two is a gap in the file" (snippet-level, secondary; [boringfloor](https://boringfloor.com/blog/agents-md-best-practices/)). Severity overrides frequency: a destructive or security-relevant mistake justifies a hard stop after one occurrence, which is Shingo's distinction between control and warning devices (secondary; [qms2go](https://qms2go.com/learn/blog/correcting-human-errors-the-japanese-way-with-poka-yoke)). A proposed rule should then pass four tests drawn from Google's criteria: a program can decide it, the fix is stated and easy, it has no legitimate exceptions if it will block, and it will plausibly recur or is costly when it does.

The mechanism follows from the shape of the mistake. This ladder is a synthesis of the practitioner sources and has no empirical validation.

| Mistake shape | Best home | Enforcement |
|---|---|---|
| A raw API or pattern that should never be used | Wrapper API or type, plus a ban on the raw form | Blocking |
| Syntactic or single-file pattern (banned call, restricted import) | Config-only lint rule, ast-grep or Semgrep pattern | Blocking once clean on the codebase |
| Cross-module shape (layering, file size, naming) | Import-graph contract or structural test | Blocking with a baseline |
| Behavioural bug | Regression test written to fail first | Blocking |
| Process step (format, do not edit protected files) | Agent hook, then the same check in CI | Blocking in CI |
| Preference with exceptions, or a judgment call | One line of prose, or a reviewer standard | Advisory |
| First occurrence, plausibly task-specific | Nothing yet | None |

Five craft points separate a rule that helps from one that harms. The first is to prove the rule fires: save the bad snippet and the corrected snippet as fixtures, require a hit on one and silence on the other, then run the rule over the whole repository to count existing hits before enabling it. The second is to write the message as the next prompt the agent reads. OpenAI's lints reportedly carry remediation instructions (secondary; [Commonplace notes](https://zby.github.io/commonplace/sources/harness-engineering-leveraging-codex-agent-first-world/)), and Discourse's lint guide prescribes "Use <preferred> instead of <current>: <specific guidance>." (snippet-level; [discourse/lint-configs](https://github.com/discourse/lint-configs/blob/main/AI-AGENTS.md)). No measurement shows remediation text improves fix rates, but a message that names the permitted route also gives the agent an alternative to bypassing. The third is to baseline existing violations and ratchet, so the rule can be enforced on new code today; ESLint's bulk suppressions and Notion's per-file ratchet are the documented patterns (snippet-level; [ESLint blog](https://eslint.org/blog/2025/04/introducing-bulk-suppressions/); [Notion](https://www.notion.com/blog/how-we-evolved-our-code-notions-ratcheting-system-using-custom-eslint-rules)).

The fourth is to protect the checker and police the escape hatch. Lint configuration, baselines, hooks and CI definitions belong on a protected-path list, with `Edit` deny rules and a `PreToolUse` hook locally ([permissions docs](https://code.claude.com/docs/en/permissions)) and the same check re-run in CI, because CI is the only layer outside the agent's reach. Each suppression should name one rule and carry a reason, unused suppressions should be errors, and the agent should be told that a suspected false positive is something to stop and report. The fifth is to prune. Each rule needs an owner and a record of the incident that produced it; rules with zero hits or heavy suppression get deleted or demoted, and the prose line a check replaces gets deleted too. Agents can now write rules almost for free, so human approval of new rules and baseline growth becomes the scarce control. That last point is inference; no published policy on it was found.

## Craftflow routes failures to linters that never fail

The repository survey shows a project that already believes the thesis. The retro skill's rubric sends repeated remediation cycles sharing "one mechanical defect shape" to a "deterministic check" and states: "Mechanical violations become checks; judgment issues become reviewer prose rules. Never propose adding steering-file bloat." ([retro SKILL.md](../plugins/craftflow/skills/retro/SKILL.md)). The learn-distiller acts only on clusters with two or more occurrences ([learn-distiller.md](../plugins/craftflow/agents/learn-distiller.md)). The docs-rot check is a proper ratchet whose baseline "may only shrink" and which fails closed ([craftflow_docs_rot.py](../plugins/craftflow/scripts/craftflow_docs_rot.py)), and the reliability-gates ledger has a manual `experimental → soak → blocking` promotion path ([craftflow_reliability_gates.py](../plugins/craftflow/scripts/craftflow_reliability_gates.py)). Memory and protected writes are enforced by hooks in block mode ([hook-mode.json](../plugins/craftflow/config/hook-mode.json)). The gaps are in where the pipeline ends and in how the repository treats its own code.

| Finding in the survey | Recommendation |
|---|---|
| `craftflow_arch_lint.py` "never fails a workflow" and exits 0 with findings, yet it is a named destination for retro's deterministic-check proposals | Give each rule in `arch-rules.json` a mode, and reuse the reliability-gates promotion path so a rule can graduate from advisory to blocking after it stays clean. Record origin incident, owner and date beside the existing WHAT/WHY/FIX text. |
| `craftflow_clean_state_check.py` detects newly added disable comments but "never blocks" | Make a new suppression without a named rule and a reason a blocking finding. This is the anti-bypass layer the rest depends on. |
| 320 `# noqa` comments in 92 files, 15 `# type: ignore`, and no linter configuration tracked | Confirm whether Ruff runs in the source monorepo. If it does, ship its configuration in this subtree; if not, the comments are inert. Use `ruff.toml`, not `pyproject.toml`, because the bundled pre-commit script treats a `pyproject.toml` as a signal to run pytest, which this repo does not use. Enable unused-`noqa` reporting ([RUF100](https://docs.astral.sh/ruff/rules/unused-noqa/), snippet-level) and ratchet the suppression count. |
| The guardrails file caps files at 500 lines; 61 of 209 Python files exceed it and nothing checks it | Add a file-size check with a shrink-only baseline, modelled on docs-rot, or relax the sentence. A rule that a third of the codebase breaks teaches agents that the file is negotiable. |
| "Functions ~30-40 lines" is prose only | Leave it as reviewer guidance. It is a proxy for a judgment call and a poor candidate for a gate. |
| "No `any` / `@ts-ignore` without an inline justification" in a repository with no TypeScript | Replace it with the Python equivalent (justified `noqa` and `type: ignore`), enforced by the suppression check above. |
| The guardrails file cites `AI_FIRST.md`, `docs/ai/decisions/` and a CI path that do not exist in this checkout | Add a docs-rot check that every path named in `AGENT_CRITICAL_GUARDRAILS.md` resolves, or state at the top that the file describes the source monorepo. |
| No CI workflow, no installed pre-commit hook, and a release gate whose path assertion cannot hold here | Decide whether this checkout is a read-only mirror. If people or agents develop in it, expose a subset gate that runs here (hook unit tests, fixture suite, version consistency, docs-rot) and wire it to pre-commit and to the opt-in stop-verify hook, which is off by default. |
| Baselines and mode files are the checks' own soft spots | Verify that `protectedWrites` covers `docs-rot-baseline.json`, the known-failures list, `hook-mode.json`, `policy.json` and `arch-rules.json`. The survey did not establish which paths are protected. |

Two smaller observations follow from the same survey. The plugin ships an AGENTS.md validator for consumer repositories but has no AGENTS.md of its own and applies no validator to its guardrails file ([agents-md-validation.md](../plugins/craftflow/skills/ai-first-setup/references/agents-md-validation.md)); running its own product on itself would be the cheapest credibility gain available. And the hooks README's admission that the Bash guard is "a hand-rolled lexer that kept opening holes across five fix cycles" ([hooks README](../plugins/craftflow/hooks/README.md)) is a reminder of what a deterministic check costs when the property is hard to decide: that guard needs the differential test against real bash that the README already recommends, more than it needs further rules. One unknown limits all of this: the source monorepo was not available, so some of these gaps may already be closed upstream.

## Conclusion

The practice changes what a mistake is worth. A corrected mistake that lives only in a conversation is lost, one written into an instruction file becomes a permanent tax with uncertain yield, and one encoded as a narrow, well-messaged check becomes just-in-time context that costs nothing until needed and announces its own obsolescence through friction. That last property is the underrated one: a stale prose rule fails silently, while a stale check produces suppressions someone can count. The same property makes the suppression count, not the rule count, the health metric to watch.

The corollary is that cheap rule authoring shifts the hard work from writing rules to refusing and retiring them. Teams that adopt "every mistake becomes a rule" literally will rebuild the false-positive problem that ended Google's first static analysis rollout, now with an agent that is better than any human at finding a way past the gate. For craftflow the next step is small and specific: its failure-mining pipeline already ends in the right proposal, and what is missing is a destination that can say no.
